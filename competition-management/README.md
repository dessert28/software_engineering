# 数学建模比赛管理系统

> 当前主线。软件工程课程 6 次实验全部围绕这个系统展开。

---

## 这是什么

一个面向校内/校际数学建模竞赛的全流程管理平台，覆盖从赛事发布到结果归档的完整生命周期。

核心目标是把现在「微信群 + 邮箱 + Excel」的线下流程搬到线上，并且做到三点：

1. **提交可靠**：分块上传 + MD5 秒传 + 版本管理，截止时间由服务端判定
2. **评审公正**：匿名评审 + 回避关系 + 评分留痕 + 审计可查
3. **AI 可控**：AI 只做预评级和分流参考，边界判定交给确定性规则，最终成绩永远由人决定

## 设计文档概览

### 平台愿景（`docs/平台愿景初稿.md`）

一页纸的模块划分，共 5 个模块：

| 模块 | 包含 |
|---|---|
| 登录注册 | 学生 / 教师 / 评委 / 平台管理员四类角色 |
| 赛事中心 | 赛事介绍、通知公告、参赛咨询、跳转报名 → 提交作品 → 我的成绩 |
| 个人中心 | 个人信息、我的竞赛（关注 / 已报名含赛程倒计时 / 比赛中 / 已结束） |
| 首页 | 内容待定 |
| 关于我们 | 内容待定 |

### 系统边界（`docs/boundary.md`）

- **生命周期 12 态**：草稿 → 报名开放 → 报名截止 → 资格审核 → 比赛进行中 → 材料提交 → 提交截止 → 评审中 → 结果待发布 → 结果发布 → 申诉/复核 → 已归档
- **角色边界**：6 类角色（赛事管理员 / 评审专家 / 指导教师 / 队长 / 队员 / 系统运维）
- **匿名评审机制**：专家看到的材料不含队伍、学校、指导教师信息
- **归档只读**：归档后数据不可修改，仅可导出

### 功能需求（`docs/functional-requirements.md`）

FR-001～FR-028 共 28 条功能需求，按 P0（MVP）/ P1（V1）/ P2（V2）分级，每条带验收条件。

配套的非功能需求：NFR-01 响应时间 ≤ 2s、NFR-02 安全、NFR-03 移动端适配、NFR-04 可追溯。

### 技术选型（`docs/tech-stack/tech-stack-python.md`）

**纯 Python 后端**，模块化单体起步：

| 层 | 选型 |
|---|---|
| 前端 | React 18 + Vite 5 + TypeScript + Ant Design 5 + TanStack Query |
| API | FastAPI + Uvicorn（多 worker） |
| 业务运行时 | SQLAlchemy 2.0 async + asyncpg（**全 async**） |
| 数据库 | PostgreSQL 16 |
| 缓存 / 队列 | Redis 7 + Celery 5 |
| 对象存储 | MinIO（S3 兼容） |
| 文档处理 | PyMuPDF + python-docx（在独立队列中执行） |

关键纪律：**所有路由 `async def`、所有 DB 调用 `await`、所有 CPU 密集任务进 Celery**。违反这条会让 uvicorn worker 的事件循环假死，是纯 Python 栈最容易踩的坑。

高并发设计分四层扩展梯度（单机 <300 → 池化 300-1000 → 水平拆分 1000-5000 → 分片 >5000），详见该文档第 9 章。

## AI 使用原则

课程实验要求人机协同开发，同时对 AI 参与范围有明确要求。本项目遵循：

| 原则 | 做法 |
|---|---|
| 过程留痕 | 每次实验记录 `ai_log.md`（提示词 + 产出）与 `ai_audit.md`（人工核对结论） |
| 责任在人 | 关键判断（需求取舍、评分规则阈值、架构决策）由人做，AI 只提供候选方案 |
| 不虚构 | 访谈记录、姓名学号、投票数、原型链接等必须真实，不得由 AI 生成 |

汇总口径见 [ai-log/README.md](ai-log/README.md)。
